# EPISODE 02: INSIDE AN AI AGENT — WHO ACTUALLY RUNS THE LOOP?

## Overall Objective

Create an 11–14 minute educational video (target: 13:00) that continues directly from Episode 01 ("What Is Agentic AI?").

Deliverables:
- **ONE final end-to-end video**, voiced and subtitled in **English**.
- **ONE separate Hindi voiceover MP3 file**. It is a highly accurate Hindi version of the complete English narration, timed to match the final video so it can be laid over the same video later.

The video itself contains English audio only. Hindi audio is never mixed into the video.

Episode 01 taught WHAT an agent is and showed the loop: GOAL → DECIDE → ACT → OBSERVE → EVALUATE.
Episode 02 opens that loop up and shows HOW it actually works underneath.

The viewer should finish the video with a clear understanding of:
- That an AI model can only receive text and produce text. It cannot run anything by itself.
- That a model does not remember previous calls on its own.
- What a **Harness** is: the program around the model that runs the loop.
- How a conversation is stored as a list of **Messages** with roles (System, User, Assistant, Tool).
- How a **Tool** is described to a model (name, description, parameters).
- How **Tool Calling** works step by step: the model *requests* an action, the harness *performs* it.
- What the **Context Window** is and why it is limited.
- How and when the loop stops.

The audience is the same as Episode 01: beginners. Assume they have watched Episode 01, but recap briefly. No programming knowledge is required. Small simplified "data cards" are allowed (see Visual Language), but there must be no real source code on screen.

The ending should lead into Episode 03 (Context Management and Memory).

## Visual Language (Define Once, Reuse Everywhere)

Fallback palette, used only if Episode 01's palette cannot be reused:
- Background: very dark navy (#0F1420)
- Primary text: off-white (#EDEFF3)
- Muted text / lines: grey (#8A93A6)
- Accent for MODEL: blue (#4C8DFF)
- Accent for HARNESS: amber (#F2B33D)
- Accent for TOOLS: green (#3DD68C)
- Warnings / errors: soft red (#FF5C5C)

Recurring visual elements. Build each one as a reusable function or class:

1. **MODEL BOX**: a rounded blue rectangle labelled "AI MODEL". Text goes in on the left and comes out on the right. It never touches files, terminals or the internet directly.
2. **HARNESS FRAME**: a larger amber rounded rectangle that *surrounds* the Model Box, labelled "HARNESS". Tools sit outside the Model Box but inside or attached to the Harness Frame.
3. **MESSAGE CARD**: a horizontal card with a small coloured role tag on the left and short English text on the right. Role tag colours:
   - SYSTEM: grey
   - USER: white
   - ASSISTANT: blue
   - TOOL: green
4. **MESSAGE LIST**: Message Cards stacked vertically, newest at the bottom. It grows over time. Old cards never disappear unless the scene is specifically about the context window.
5. **TOOL CARD**: a green card showing a tool definition with three labelled rows: NAME, DESCRIPTION, PARAMETERS.
6. **TOOL CALL CARD**: a blue card (because the model produces it) with two rows: TOOL: read_file, INPUT: path = "config.txt". Use a dashed border to show it is only a *request*, not an action.
7. **CONTEXT WINDOW**: a tall container outline. Message Cards fill it from top to bottom. A thin fill meter on the side shows how full it is.
8. **LOOP DIAGRAM**: the Episode 01 loop (GOAL → DECIDE → ACT → OBSERVE → EVALUATE, with REPEAT back to DECIDE). The active stage glows. The others are dimmed.

Data on cards must be short, readable and simplified. Do not show raw JSON, brackets-heavy syntax, or any vendor-specific API format.

## Technical Accuracy Rules (Must Not Be Violated)

The narration and visuals must never imply any of the following:
- That the model itself opens files, runs commands, or visits websites. The model only produces a *request*; the harness executes it.
- That the model remembers previous conversations or previous calls by itself. Continuity exists only because the harness sends the message history again on every call.
- That the context window is unlimited.
- That a tool call is guaranteed to be correct. The model can request the wrong tool or wrong input.

Say these things clearly in the narration:
- "On every single call, the harness sends the whole conversation to the model again."
- "The model decides. The harness does."
- "If the model's reply contains no tool request, the harness treats it as the final answer and the loop stops."

Do not introduce: MCP, specific APIs or SDKs, JSON Schema by name, tokenizer internals, transformers, embeddings, vector databases, or planning algorithms. Those belong in later episodes.

# VIDEO STRUCTURE

## 01. Recap and Hook: Who Runs the Loop?
TIME: 0:00–1:00

Open on the Episode 01 loop diagram, fully lit. Briefly recap (about 20 seconds): an agent receives a goal, decides, acts using tools, observes the result, evaluates, and repeats.

Then create the hook:
- Zoom into the MODEL component.
- Show a "read file" action trying to come out of the Model Box and bouncing off its edge.
- On-screen question: "A model only produces text… so who opens the file?"

Narration idea: In the last lesson we said the agent "reads files" and "runs commands". But a model only produces text. So who actually does these things? Today we open the agent and look inside.

Show the title card: **INSIDE THE AGENT**

## 02. The Model Only Produces Text
TIME: 1:00–2:15

Establish two facts about the model.

FACT 1: Text in, text out.
- Show the Model Box. A text card goes in and a text card comes out.
- Show icons of a file, a terminal and a globe outside the box, separated by a faint wall. The model cannot reach them.

FACT 2: The model does not remember by itself.
- Call 1: USER card says "My name is Rahul." The model replies "Hello, Rahul!"
- The Model Box "resets": a quick fade or flash.
- Call 2 (sent separately): USER card says "What is my name?" The model replies "I don't know."
- Explain that each call is independent. The model starts fresh every time unless someone gives it the earlier conversation again.

End with the question (on screen, English): "So how do ChatGPT or Claude remember what you said earlier?" This leads into the next section.

## 03. Meet the Harness
TIME: 2:15–3:30

Introduce the Harness. Animate the amber HARNESS FRAME growing around the Model Box.

Definition (say this clearly): A harness is the ordinary program built around the model. It runs the agent loop, talks to the model, and actually performs the actions.

Analogy (animate it simply):
- A decision-maker sits in a closed room with no doors, only a slot for passing paper.
- An assistant sits outside the room.
- The assistant slides in a note: the full situation so far.
- The decision-maker writes back: "Open the file named config.txt and tell me what it says."
- The assistant opens the file, writes down what it says, and slides the whole updated note back in.
- Map it on screen: decision-maker = MODEL, assistant = HARNESS, file = TOOL.

List the harness's responsibilities, appearing one by one around the frame:
1. Stores the conversation.
2. Sends the conversation to the model.
3. Reads the model's reply.
4. Executes the tools the model requests.
5. Sends the results back.
6. Decides when to stop.
7. Enforces permissions and limits.

Key line:
- English (video): "The model decides. The harness does the work."
- Hindi (MP3): "Model फ़ैसला लेता है। Harness काम करता है।"
On-screen (English): **The model decides. The harness does.**

Clarify: an "AI agent" = model + harness + tools working together. This links back to Episode 01's point that a model alone and an agent are not the same thing.

## 04. The Conversation Is a List of Messages
TIME: 3:30–5:00

Answer the question from Section 02.

Show the MESSAGE LIST. Introduce the four roles one at a time, each with its coloured tag:
1. **SYSTEM**: instructions from the developer that set the agent's behaviour and rules. Example card: "You are a helpful coding agent. Ask before deleting any file."
2. **USER**: what the person asks. Example: "My name is Rahul."
3. **ASSISTANT**: what the model replies. Example: "Hello, Rahul!"
4. **TOOL**: results returned by tools. Introduce it here, but explain it in Section 06.

Replay the memory example from Section 02, this time correctly:
- The list holds: SYSTEM, USER "My name is Rahul.", ASSISTANT "Hello, Rahul!", USER "What is my name?"
- Animate the *entire list* travelling into the Model Box as one bundle.
- The model replies: "Your name is Rahul."
- A new ASSISTANT card is added to the bottom of the list.

Key line: on every single call the harness sends the *whole* conversation again. This is how the model appears to "remember". The memory lives in the harness, not in the model.

Show a counter: "Call #1, Call #2, Call #3…" with the bundle getting slightly bigger each time. This plants the idea for Section 07.

## 05. How the Model Learns About Tools
TIME: 5:00–6:15

Ask: if the model cannot see the computer, how does it know which tools exist?

Answer: the harness sends a short description of each available tool along with the messages.

Show a TOOL CARD:
- NAME: read_file
- DESCRIPTION: Reads the text inside a file
- PARAMETERS: path (which file to read)

Then show two more cards, smaller, beside it:
- run_command: Runs a command in the terminal (parameter: command)
- edit_file: Changes the text of a file (parameters: path, new_text)

Animate the three tool cards being attached to the bundle that goes into the Model Box, together with the Message List.

Explain:
- The model only sees these descriptions. It never sees the tool's actual program.
- A clear description helps the model choose correctly. A vague one causes mistakes.
- Animate a short example: a vague description ("does file stuff") makes the model hesitate with a "?" icon. A clear one makes the model pick the tool confidently.

## 06. Tool Calling, Step by Step
TIME: 6:15–8:15

THIS IS THE MOST IMPORTANT SECTION OF THE VIDEO. Go slowly. Keep the Message List visible on the right side of the screen the whole time and add each card as it happens.

Example task: USER: "What port does the server use in config.txt?"

Animate each step, with a step number visible on screen:

1. **Harness sends**: SYSTEM + USER messages + tool descriptions → Model Box.
2. **Model replies with a TOOL CALL CARD** (dashed blue border): TOOL: read_file, INPUT: path = "config.txt".
   Pause here. Stress that this is only a *request* written as text. Nothing has happened yet. The card is added to the list as an ASSISTANT message.
3. **Harness reads the reply** and sees a tool request.
4. **Harness checks permission**: a small shield icon gets a green tick.
5. **Harness executes the tool**: the read_file tool lights up green, a file icon opens, and text is extracted.
6. **Harness adds the result** as a TOOL message: "port = 8080, host = localhost".
7. **Harness calls the model again**, sending the whole updated list.
8. **Model replies with normal text, no tool request**: "The server uses port 8080."
9. **Harness sees there is no tool request**, so it treats this as the final answer and shows it to the user.

Then map it back to Episode 01. Bring the LOOP DIAGRAM in beside the steps and connect them with light lines:
- DECIDE = the model writes the tool request (step 2)
- ACT = the harness executes the tool (steps 4–5)
- OBSERVE = the result is added as a TOOL message (step 6)
- EVALUATE = the model reads the result on the next call and decides whether more work is needed (steps 7–8)

Key line:
- English (video): "The agent loop isn't magic. It's a simple program loop: ask the model, do what it requests, add the result, and ask again."
- Hindi (MP3): "Agent Loop कोई जादू नहीं है। यह एक सीधा-सा Program Loop है: Model से पूछो, उसकी request पूरी करो, result जोड़ो, और फिर से पूछो।"
On-screen (English): **Ask the model → do what it requests → add the result → ask again.**

Briefly show a second variation (about 15 seconds): the tool fails (file not found). The harness does not crash. It adds a TOOL message "Error: config.txt not found" and the model then decides to search for the file with another tool. This shows that errors are also feedback.

## 07. The Context Window: The Model's Limited Desk
TIME: 8:15–9:45

Introduce the CONTEXT WINDOW container.

Explain:
- Everything sent to the model in one call (system message, all messages, tool descriptions, tool results) must fit within a fixed limit. This limit is called the **Context Window**.
- The limit is measured in **Tokens**. Simple definition only: a token is a small piece of text, often a part of a word. Do not explain how tokens are created.
- Analogy: a desk of fixed size. Every paper must fit on the desk at the same time.

Animate:
- Message cards filling the container while the fill meter rises.
- A single huge TOOL result (for example, reading a very large file) drops in and takes up most of the space, and the meter jumps.
- The meter reaches the top and turns red.

What happens when it is full (say all three, briefly):
1. The request can fail.
2. The harness must remove or shorten older messages.
3. Or it can replace older messages with a short summary.

Also mention: a longer context generally makes each call slower and more expensive.

Key point: deciding what stays on the desk is one of the hardest problems in building agents. It is called **Context Management**, and it will be the topic of the next lesson. Do not explain techniques in detail here.

## 08. When Does the Loop Stop?
TIME: 9:45–10:45

Show the loop spinning, then explain the ways it ends:

1. **Normal stop**: the model replies without any tool request, so the task is considered finished.
2. **Step limit**: the harness allows only a maximum number of loop iterations, for example 20. Show a counter reaching its limit and the loop halting with a red stop icon. This protects against endless loops.
3. **Human approval**: before a risky tool (delete a file, run a dangerous command), the harness pauses and asks the user. Show an "Allow this action? Yes / No" prompt.
4. **The model asks a question**: if information is missing, the model replies with a question to the user instead of guessing, and the loop waits.

Connect to Episode 01's "Agents Are Not Magic" section: these safeguards are written into the harness by its developer. Human oversight is a deliberate part of the design.

## 09. Full Replay: The Bug-Fixing Agent, From the Inside
TIME: 10:45–12:15

Replay Episode 01's bug-fixing example, but this time at the message level. Keep it fast-paced and rhythmic, because the viewer now understands each part.

Split the screen: Message List on the left, Loop Diagram on the right (active stage glowing).

Message sequence (each card slides in; the loop stage highlights at the same time):
1. USER: "The program is crashing. Find the bug and fix it."
2. ASSISTANT (tool call): run_command → "run tests"
3. TOOL: "Test failed: wrong result in total()"
4. ASSISTANT (tool call): read_file → "math_utils.py"
5. TOOL: (short code-like snippet shown as a blurred or abstract block, not readable code)
6. ASSISTANT (tool call): edit_file → "math_utils.py"
7. TOOL: "File updated successfully"
8. ASSISTANT (tool call): run_command → "run tests"
9. TOOL: "All tests passed ✓"
10. ASSISTANT (final text, no tool call): "Bug fixed. total() was adding the numbers incorrectly."

Show a small "Call #N" counter on the Model Box that increments with every assistant message, to reinforce that each step is a new call with the full history.

Show the context meter at the side rising slowly through the replay.

End with the harness showing the final message to the user and the loop going quiet.

## 10. Conclusion and What's Next
TIME: 12:15–13:00

Summarize with five short English lines appearing one by one on screen:
1. A model only reads text and writes text.
2. The harness is the program around the model that runs the loop.
3. The whole conversation is sent to the model as messages on every call.
4. The model requests a tool; the harness runs it.
5. The context window is limited, so what to keep and what to drop matters.

The narration should communicate something along these lines.

English (video):

"Today we looked inside an agent. We saw that the model doesn't actually do any work by itself. It only makes decisions. The real work is done by the harness. And the whole conversation is sent to the model again, from the start, every single time.

But one big problem is still left. The context window is limited. The more work an agent does, the more messages pile up. And at some point, it runs out of space.

So how does an agent finish big tasks? How does it remember what's important and let go of what isn't?

That's exactly what we'll learn in the next lesson: Context Management and Memory."

Hindi (MP3), the accurate Hindi equivalent of the lines above:

"आज हमने Agent के अंदर झाँककर देखा। हमने समझा कि Model ख़ुद कोई काम नहीं करता, वह सिर्फ़ फ़ैसला लेता है। असली काम Harness करता है। और पूरी बातचीत हर बार नए सिरे से Model को भेजी जाती है।

लेकिन एक बड़ी समस्या अभी बाकी है। Context Window सीमित है। Agent जितना ज़्यादा काम करता है, उतने ज़्यादा Messages जमा होते जाते हैं। और एक समय के बाद जगह ख़त्म हो जाती है।

तो Agent बड़े काम कैसे पूरे करेगा? वह ज़रूरी चीज़ें कैसे याद रखेगा और फ़ालतू चीज़ें कैसे हटाएगा?

अगले lesson में हम ठीक यही सीखेंगे: Context Management और Memory।"

Finish with a minimalistic title card in the same style as Episode 01:

AGENTIC AI
INSIDE THE AGENT

Fade in a smaller line underneath for 2 seconds: "Next: Context & Memory"
